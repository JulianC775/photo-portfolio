# CLAUDE.md

Personal photography portfolio: a small curated public gallery (landscape/astro/timelapses) plus a
password-gated `/friends` area where friends download full-resolution photos of themselves,
organised by event.

**`docs/PLAN.md` is the design doc.** Requirements in Part 1, architectural decisions with
reasoning in Part 2, milestones in Part 3, the Pi bring-up checklist in Part 5. Read it before
non-trivial work. If the code diverges from a decision there, update the doc in the same commit.
`docs/PI-SETUP.md` is the operational runbook for the storage backend.

## Local development

The storage backend doesn't exist yet, so development runs against generated fixtures:

```bash
npm run seed        # writes fake photos + a manifest into .dev-media/ (gitignored)
npm run dev:media   # terminal 1 — serves .dev-media/ on :4321, standing in for the Pi
npm run dev         # terminal 2 — with NEXT_PUBLIC_MEDIA_URL=http://localhost:4321
```

Two origins on purpose: production serves media from a different host than the app, and collapsing
that into `public/` locally would hide breakage until deploy. `npm test` needs none of this.

## Stack

Next.js (App Router) · React · TypeScript · Tailwind · deployed on Vercel.
`sharp` + `exifr` + `archiver` (CLI only, never at request time) · `zod` · `jose` ·
`@aws-sdk/client-s3`.

## Storage model

Media and metadata live in S3-compatible object storage. Two buckets on two providers (D3,
hybrid): the public one on a Raspberry Pi 5 running MinIO behind a Cloudflare Tunnel at
`media.catellolens.com`, the private one on Cloudflare R2 because its bytes are never cached and
would otherwise crawl out through the house's upload line.

| | where | contents | access |
|---|---|---|---|
| `portfolio-public` | Pi | web derivatives, `content/public.json` | anonymous read, edge-cached |
| `portfolio-private` | R2 | full-res originals, per-event zips, `content/friends.json` | presigned URLs only, **never cached**; CLI-capped at 9.5 GB |

Manifests are JSON objects **in the buckets, not in git** — adding a photo must never require a
commit or a redeploy.

**Buckets are serving copies, not the archive of record.** Full-resolution originals live on the
owner's PC; anything in either bucket can be regenerated by re-running the upload CLI — *except
the manifests*, which hold metadata that exists nowhere else. Hence invariant 7.

## Invariants

Breaking any of these is a bug, not a style preference.

1. **No media in the repo.** No images or video in git, ever, at any size.
2. **Public images carry no GPS EXIF.** The CLI must re-read a generated derivative and fail the
   upload if any GPS tag survives. Never rely on `sharp` stripping metadata by default without
   asserting it.
3. **Friends' originals are byte-for-byte untouched**, full EXIF intact.
4. **`/friends/*` is never indexable** — `noindex`, absent from `sitemap.ts`, not linked from the
   main nav (only a small footer/banner link).
5. **No secrets in code.** Env vars only — plus the gitignored `friends-passwords.json`, which
   never leaves the owner's PC. Document every env var in `.env.example`.
6. **Media bytes never pass through Vercel.** Downloads are 302s to presigned URLs; images are
   pre-generated and served `unoptimized` from the media domain.
7. **Every manifest write mirrors to the local machine** (`LOCAL_MANIFEST_MIRROR`) as part of the
   same command. It is the only data on the Pi that cannot be regenerated.
8. **Categories and events are data, never code.** `z.string()` validated against the manifest's
   category list — never `z.enum`, never category literals in JSX, never a `switch` on category.
   Adding one must not require a deploy.

## Boundaries

Three modules are the only ones that know their respective concerns. Keep it that way — each was
chosen so the backing decision can change in one file.

- `src/lib/storage/` — the only code aware of the storage provider.
- `src/lib/content.ts` — the only code that reads or writes manifests.
- `src/lib/auth/` — password checking returns a `Grant`, never a boolean, which is what let
  per-event passwords land without reworking the flow: `checkPassword(input, event?)` answers
  `{ scope: { event } }` for an event's own password, `{ scope: 'all' }` for the owner's master.

## Adding photos

```bash
npm run upload -- ./shot.jpg --public --category astro --title "..."   # public gallery
npm run upload -- ./event/*.jpg --event "Camping Trip 2026"            # friends event
npm run passwords                                                      # set its password
```

Uploads go straight from the local machine to the Pi (LAN speed when home), then the CLI pings
`/api/revalidate` so the site reflects them within seconds. Re-running skips files already in the
manifest, so interrupted batches resume. A friends upload ends by rebuilding that event's
"Download all" zip on the Pi (`npm run zip -- "Event"` does it by hand — D6).

A new friends event has no password, so nobody can open it yet and it isn't listed on
`/friends/login`. Add an `"Event Name": "the passphrase"` line to `friends-passwords.json` at the
repo root — plaintext, gitignored, owner's PC only; copy `friends-passwords.example.json` to start —
then run `npm run passwords`, which hashes each one onto the matching event in the manifest. No
deploy needed. That file is the source of truth: delete a line, re-run, and that access is revoked.

## Conventions

- Server Components by default; `'use client'` only where interaction genuinely requires it. Two
  Client Components: the login form (`useActionState`'s inline error + pending state) and the
  friends event grid (checkbox selection — and it renders its own cards from data, because a
  server-rendered tree ships twice, HTML plus hydration payload, which at 212 photos was most of
  a 1.4 MB page). The category filter and the gallery-picker on `/friends/login` are plain links
  (real URLs, no JS). An overlay lightbox is the remaining candidate.
- Explain non-obvious architectural choices in comments or the PR — the owner has ~1.5 years of
  React and asked for reasoning, not just working code.
- Dark, photo-forward, minimal chrome. Typography supports the images rather than competing.
- Don't add pagination, caching layers, or abstraction the current volume doesn't need (~40 public
  photos, hundreds of friends photos). Simplicity is an explicit requirement.
